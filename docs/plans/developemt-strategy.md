# J DMP Converter 開発戦略および機能・非機能要件

## 0. 背景

国内の公的研究資金の助成機関の一部は、研究者に対してデータマネジメントプラン（DMP）の作成と提出を要求しています。以下にそれらの助成機関情報のリストを共有いたします。これらの助成機関のDMPおよび研究データのメタデータ（Metadata）のスキーマはバラバラです。そのため研究者は、ある助成機関の要求に応じて作成したDMPファイルやMetadataファイルを他の助成機関への申請の際に再利用することに非常に苦労することとなり、正直彼らは運罪していると聞いています。また、これらのDMP様式やMetadata様式を扱うサービスが存在しません。そのため国内の学術機関がそれぞれ独立したやり方でこれらのDMPおよびMetadata形式をサポートするシステムを開発しています。このような現状では、いずれどの大学もギブアップする危険があります。

そこで、これらのDMP様式およびMetadata様式を包括的に扱い、各機関や研究者にDMP様式間の変換やMetadata様式間の変換機能を提供するツールを開発します。本資料は、その開発の戦略と、ありえる機能要件・非機能要件を提示します。

## 1. 開発戦略 (Development Strategy)

単に「AからBへ変換する」プログラムを個別に書くと、組み合わせ爆発（）が起き、メンテナンス不能になります。以下の3つの戦略を柱とすべきです。

### 戦略1：ハブ＆スポーク型アーキテクチャ（共通中間表現の導入）

各機関の様式（Excel/Word）を直接相互変換するのではなく、**「共通中間表現（Common Intermediate Representation: CIR）」**を定義し、それを経由させます。

* **メリット:** 新しい助成機関が増えても、その機関とCIRとの変換アダプタを作るだけで済みます。
* **標準規格の採用:** CIRには、国際的な標準である **RDA (Research Data Alliance) DMP Common Standard (maDMP)** をベースにしつつ、日本の商習慣（e-Rad研究者番号など）を拡張したJSONスキーマを採用することを推奨します。

### 戦略2：テンプレートエンジンの分離（ロジックと様式の分離）

「データの保持（JSON）」と「帳票の出力（Excel/Word）」を完全に分離します。

* 助成機関は頻繁にExcelのセルの位置やフォントを変更します。これをプログラムコード（Hard-coding）に埋め込むと修正が大変です。
* Excel/Wordファイルを「テンプレート」として読み込み、プレースホルダー（`{{project_name}}`のようなタグ）にデータを流し込む方式（Jinja2 likeなアプローチ）を採用し、様式変更への追従コストを下げます。

### 戦略3：エコシステム連携とオープンソース化

* **e-Rad連携:** 科研費番号やe-Rad研究者番号を入力キーとして、基本情報（所属、職位、研究課題名）を自動補完する機能を視野に入れます。
* **OSS化:** 一大学で抱え込むには重すぎる課題です。基本エンジンをOSS（オープンソース）化し、国立情報学研究所（NII）のRCOSや、各大学のURA（リサーチ・アドミニストレーター）コミュニティが「Excelテンプレート定義ファイル」を共同でメンテナンスできる体制を目指すべきです。

## 2. 機能要件 (Functional Requirements)

ツールが具体的に提供すべき機能です。

### A. データ取り込み・入力 (Input)

1. **マルチフォーマット・インポート:**
    * 既存のExcel (XLSX) および Word (DOCX) のDMP/Metadataファイルをドラッグ＆ドロップで読み込み、システム内の共通データモデルに変換する機能。
    * ※Wordは構造化が難しいため、AI（LLM）を活用した「非構造化テキストからの項目抽出」補助機能を検討する価値があります。

2. **ウィザード形式エディタ:**
    * Webブラウザ上で、共通項目（プロジェクト名、PI名、データ種別、保存期間など）を入力するフォーム。
    * 「一度入力すれば、すべての様式に反映される」体験を提供。

### B. データ変換・マッピング (Transformation)

3. **スキーマ・マッピング機能:**
    * 「AMEDの『データ管理者』」＝「JSPSの『データ管理責任者』」といった項目の紐づけ定義を持つ。
    * 不足項目アラート：「AMEDからJSPSへ変換したいが、JSPSで必須の『メタデータ付与ルール』の情報が足りません」といった差分をユーザーに通知し、追記を促す機能。

### C. 生成・出力 (Output)

4. **様式別エクスポート:**
    * 指定した助成機関（例：AMED_DMP, NEDO_Metadata）の最新様式（XLSX/DOCX）にデータを埋め込んでダウンロードさせる機能。
    * リストにあるMETIやERCA等のXLSXだけでなく、CFAやMHLWのようなDOCX形式への書き出しもサポート。

### D. 管理・連携 (Management)

5. **バージョン管理:**
    * 申請時、採択時、終了時でDMPは更新されます。スナップショットを保存する機能。
6. **API提供:**
    * 大学の機関リポジトリや学内研究管理システムからDMPデータを取得・登録するためのREST API。

## 3. 非機能要件 (Non-Functional Requirements)

システムの品質や制約に関する要件です。

### A. 保守性・拡張性 (Maintainability)

* **スキーマ定義の外部化:** 助成機関のExcel様式が変更された際、システム本体の再コンパイルなしに、設定ファイル（YAMLやJSON）とテンプレートファイルの差し替えだけで対応できること。
* **プラグイン構造:** 新しい助成機関（例：JSTが新しい形式を出した等）を、プラグインとして追加できること。

### B. 相互運用性 (Interoperability)

* **machine-actionable DMP (maDMP) 準拠:** 生成される内部データが、機械可読な標準形式であること。これにより、将来的にNIIの研究データ基盤（NII RDC）等とのデータ交換が容易になります。

### C. セキュリティ (Security)

* **機密性:** まだ公開前の研究構想（アイデア）が含まれるため、通信の暗号化はもちろん、アクセス制御（誰がどのDMPを見られるか）を厳格に行うこと。
* **オンプレミス/クラウド両対応:** 大学によってはクラウドへのデータ保存を禁止している場合があるため、Dockerコンテナ等で各大学のサーバーにデプロイ可能な構成であること。

### D. 使用性 (Usability)

* **研究者ファースト:** 専門用語（メタデータスキーマ、DOI等）を知らなくても、「埋めるべき場所」が直感的にわかるUI。
* **ガイダンス表示:** 各機関の「記入要領」をツールチップ等でその場で見られるようにする（PDFをいちいち開かせない）。

## 4. 技術的アプローチの推奨 (Tech Stack Recommendation)

もしプロトタイプを作成されるのであれば、以下のスタックが適しています。

* **Backend:** Python (FastAPI または Django)
    * Excel操作: `openpyxl` または `pandas`
    * Word操作: `python-docx`
    * データモデル検証: `Pydantic` (JSON Schema生成に強力)

* **Frontend:** React または Vue.js
    * 動的なフォーム生成（JSON Schemaからフォームを自動生成するライブラリ活用）

* **Core Logic:**
    * **Jinja2 for Office:** `docxtpl` (Word用テンプレートエンジン) や `openpyxl` ラッパーを用いて、テンプレートファイルへの差し込み印刷的なアプローチをとるのが最も保守性が高いです。
